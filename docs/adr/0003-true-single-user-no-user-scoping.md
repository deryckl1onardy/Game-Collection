# True single-user for now, no `user_id` scoping — supersedes ADR-0001

The concrete project ("Shelf") is explicitly a personal artifact — "one place that is *yours*", not a service for others — with a single SteamID hardcoded in an env var driving the nightly sync. We decided to build genuinely single-tenant: no `users` table, no `user_id` column on `games`/`user_game`/`sessions`. This reverses ADR-0001's call to carry a speculative `user_id` from day one, because for this project multi-user isn't a cheap additive feature — it requires Steam OpenID login, a per-user (not global) SteamID for the sync cron, and per-user asset storage, none of which the current architecture sketch accounts for.

The owner wants multi-user eventually. When that's actually prioritized, the expected path is a real migration: add a `users` table, add `user_id` to the relevant tables, replace the env-var SteamID with a per-user value captured via Steam OpenID login, and make the sync cron iterate users instead of syncing one fixed account. This is deliberately deferred rather than half-built now, since a wrong-shaped speculative `user_id` (e.g. added before OpenID login exists) would likely need to be reworked anyway once real multi-user requirements are known.
